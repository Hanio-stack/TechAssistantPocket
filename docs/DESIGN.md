# TechAssistantPocket 設計・ユーザーフロー

最終更新: 2026-09-09

## 1. 何を作るか

TechAssistantPocket は、単なる Todo / Calendar アプリではなく、**ユーザーの実行履歴から「その人が予定を成功させやすい条件」を見つけ、次の予定改善につなげる iOS アプリ**とする。

コアサイクルは以下。

```text
Plan
予定を決める
↓
Do
実行する
↓
Review
完了 / 未完了を記録する
↓
Improve
成功率から次回の予定を改善する
↓
Plan
```

## 2. MVP の範囲

### 必須

- タスク作成 / 編集 / 削除
- 日時、所要時間、優先度
- 未スケジュールのタスク保持
- Today 画面
- 完了 / 未完了記録
- iPhone カレンダー参照
- 選択した iPhone カレンダーへの予定登録
- ローカル通知
- デイリーレビュー
- 実行履歴保存
- 曜日 / 時間帯 / タスクごとの成功率
- ルールベースのスケジュール変更提案

### MVP に入れない

- OpenAI API / LLM API
- チャット UI
- 自然言語によるタスク登録
- 自前バックエンド
- Google Calendar API 直接連携
- 複雑な全自動スケジューリング
- チーム / 他ユーザーとの共有

## 3. データの責務

### SwiftData

TechAssistantPocket 独自の情報を保存する。

- タスクそのもの
- 完了状態
- 実行履歴
- 優先度
- 所要時間
- レビュー
- 成功率計算に必要なデータ
- EventKit のイベントとの対応 ID

### EventKit

iPhone が管理しているカレンダーを扱う。

- ユーザーの既存予定を読む
- Pocket でスケジュールしたタスクを、指定されたカレンダーへ予定として書き込む
- Google アカウントのカレンダーが iPhone に登録されている場合、そのカレンダーを保存先として利用できる

Google Calendar を使う場合も、MVP では Pocket → EventKit → iOS の Google カレンダー → Google 同期、という構造とする。

### UserNotifications

- タスク開始前通知
- タスク開始通知
- デイリーレビュー通知

すべてローカル通知とし、通知用サーバーを持たない。

## 4. タスクとカレンダー予定の関係

タスクは必ずしも最初からカレンダー予定ではない。

```text
Task
├─ 未スケジュール
│  └─ Pocket 内だけに存在
│
└─ スケジュール済み
   ├─ SwiftData に予定日時を保存
   └─ EventKit にカレンダーイベントを作成
```

これにより「いつかやるタスク」と「時間を確保したタスク」を分ける。

### MVP の同期方針

- Pocket からスケジュールしたタスクは EventKit に作成する
- 作成した EventKit の `eventIdentifier` を Pocket 側で保持する
- Pocket から日時変更した場合は対応するカレンダーイベントも更新する
- 外部カレンダーアプリから Pocket 由来の予定が変更された場合の完全な双方向同期は初期実装では優先度を下げる
- 既存のカレンダー予定は「空き時間判定・Today 表示」のために参照する

## 5. 初回起動からのユーザーフロー

### Step 1: 初回起動

アプリの目的を短く説明する。

> TechAssistantPocket は、あなたが「予定をこなしやすい時間」を実績から見つけ、次の予定を改善するアプリです。

アカウント作成は要求しない。

### Step 2: カレンダーアクセス

EventKit の権限を要求する。

許可されたら、端末上で利用可能なカレンダーを表示する。

例:

```text
予定を書き込むカレンダー

○ iCloud / 自宅
● Google / マイカレンダー
○ Google / 仕事
```

初回に 1 つ「Pocket の既定保存先」を選ぶ。

Google Calendar を使用したいのに候補がない場合は、iPhone 側で Google アカウントのカレンダーを追加するよう案内する。

### Step 3: 通知設定

通知権限を要求する。

最初は最低限、以下を設定可能にする。

- タスク開始前通知: 例 10 分前
- デイリーレビュー: 例 22:00

通知を拒否してもアプリ自体は使用可能にする。

### Step 4: Today へ

初回設定終了後は Today 画面へ。

まだ何もなければ、最初のタスク作成を促す。

## 6. 普段の使用フロー

### A. タスクを作る

ユーザーが `+` からタスク追加。

最低入力:

- タイトル

任意:

- 日時
- 所要時間
- 優先度
- カテゴリ

日時をまだ決めない場合は未スケジュールタスクとして保存。

日時を決めた場合は EventKit に予定を作成する。

### B. Today を見る

Today はアプリのホームとする。

表示候補:

```text
今日 9/9

10:00  既存カレンダー予定
11:00  英語学習        [未完了]
13:00  昼食
19:30  BK制作          [未完了]

未スケジュール 3件
```

Pocket タスクと既存カレンダー予定を同じ時間軸で確認できるようにする。

ただし、既存カレンダー予定は Pocket の「成功率」計算対象にはしない。

### C. 通知を受ける

例:

```text
11:00から「英語学習」です
```

通知からアプリを開いて実行。

### D. 完了する

タスク終了後、ユーザーは完了を押す。

記録する情報:

- 予定日時
- 完了 / 未完了
- 完了日時
- 曜日
- 時間帯
- タスク種別
- 所要時間

完了ボタンを押さないまま一定時間 / 当日が終了したタスクは、レビュー時に未完了候補として確認させる。

### E. デイリーレビュー

設定時刻に通知。

```text
今日の振り返り

予定したタスク  5
完了             3
未完了           2
成功率          60%
```

未完了タスクについては、必要なら簡単な理由を選択できる。

例:

- 時間がなかった
- 疲れていた
- 予定が変わった
- 所要時間を見誤った
- やる気が出なかった
- その他

理由入力は MVP 初期では任意とする。

### F. 履歴が蓄積する

例:

```text
英語学習
平日 21:00-24:00  成功率 33%
休日 09:00-12:00  成功率 80%
```

最低限の母数を満たした場合だけ提案する。

例: 同条件の実績 3 回以上。

### G. 次の予定を提案する

```text
英語学習は夜より休日午前の方が
成功率が47ポイント高くなっています。

次回を土曜10:00に移しますか？

[移動する] [そのまま]
```

ユーザーが承認した場合のみ予定を変更する。

**MVP ではアプリが勝手にスケジュールを変更しない。**

## 7. 成功率ロジック v0.1

基本式:

```text
成功率 = 完了回数 / 予定回数
```

集計軸:

- 全体
- タスク別
- 曜日別
- 時間帯別
- タスク × 時間帯

時間帯の初期案:

- 朝: 05:00-12:00
- 昼: 12:00-17:00
- 夜: 17:00-22:00
- 深夜: 22:00-05:00

最初から高度な統計や機械学習は使わず、**説明可能な単純ルール**を優先する。

## 8. 提案ルール v0.1

例:

1. 同じタスク / カテゴリで実績が一定数以上ある
2. 現在予定されている時間帯の成功率が低い
3. 別の時間帯に十分な実績があり、成功率が明確に高い
4. カレンダー上で候補時間が空いている
5. ユーザーへ提案する

例:

```text
現在: 火曜 22:00
成功率: 25%

候補: 土曜 10:00
成功率: 75%

差: +50pt
→ 提案対象
```

提案には必ず「なぜそう提案したか」を表示する。

## 10. 想定データモデル

### Task

```text
id
title
category
priority
estimatedDuration
createdAt
isArchived
```

### TaskOccurrence

1 回の「実行予定」を表す。

```text
id
taskID
scheduledStart
scheduledEnd
status
completedAt
eventIdentifier
calendarIdentifier
```

`status` の例:

- scheduled
- completed
- missed
- cancelled

Task と実行予定を分離することで、繰り返しタスクや履歴分析を扱いやすくする。

### DailyReview

```text
id
date
plannedCount
completedCount
reviewedAt
```

### FailureReason（任意）

```text
occurrenceID
reason
note
```

成功率自体は履歴から計算し、初期版では集計結果を永続化しない。

## 11. 技術構成

```text
SwiftUI
   │
   ├─ SwiftData
   │   └─ Pocket 独自データ
   │
   ├─ EventKit
   │   └─ Apple / Google / その他 iOS カレンダー
   │
   └─ UserNotifications
       └─ ローカル通知
```

外部 API や常時稼働サーバーに依存しない。

## 12. 開発上の原則

- MVP は「一週間使って価値を検証できること」を優先する
- 新機能追加よりコアループ完成を優先する
- 自動化しても、ユーザーの予定を勝手に変更しない
- 提案理由を説明できるロジックにする
- 設定依存の外部サービスを増やさない
- GitHub 上の仕様を正とする
- Claude Code に実装させる際も、この仕様を読み、ビルド / テストで完了条件を検証させる

## 13. 将来候補

MVP が成立した後に検討する。

- CloudKit 同期
- 繰り返しタスクの高度化
- 自動空き時間探索
- 週次レビュー
- 成功率以外の指標
- ウィジェット
- Live Activities
- Siri / App Intents
- Google Calendar API 直接連携
- オンデバイス AI が十分使える場合の自然言語機能

ただし、追加機能が「運用コスト 0」「Local First」「予定改善」というコア思想を壊さないことを条件とする。
